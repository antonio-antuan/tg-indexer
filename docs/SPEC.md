## 1. Goal and scope

A personal tool for Antony. Burner Telegram accounts, logged in explicitly through TDLib (phone → code → 2FA), collect the text of messages from chats he selects. Messages are stored in Postgres and indexed for (a) direct keyword search and (b) natural-language questions answered by an LLM agent through MCP tools, with links to the source messages.

Reference query that must work end to end: *"what did people write in the Valencian chats over the last month about residence-permit (ВНЖ) renewal"* → a summary plus links to the messages it drew on.

**In scope (v1):** account login and session storage; chat allowlist; scheduled batch ingestion (backfill, catch-up, edit and delete sweep); Postgres storage with full-text, trigram and vector indexes; conversation windows and embeddings through a swappable provider; hybrid search; chat tags (agent proposes, Antony confirms); an MCP server exposing the search tools; a scripted reference-query check against the server (§5.7); a local CI that is the evidence of green.

**Out of scope (v1):** media, files, voice (text and captions only; a message with media stores its caption and a `has_media` flag, which is the cheap path); reactions, polls, stories; live streaming of updates; a web UI; multi-user; anything on Antony's main account; reaching the laptop from outside it (the MCP server is reachable only from containers on the same host, §5.6); registering the server in Nano's configuration (a separate later step, not part of this implementation).

**Recorded owner decisions (Antony, 2026-10-08, #584/#588/#590):** the consumer of the search tools is a NanoClaw agent in a container on the same machine, reaching the MCP server over HTTP (D-TGI-1); Telegram-deleted messages are tombstoned (D-TGI-3); the default embedding provider is Voyage AI, paid use approved (D-TGI-2); no LLM in the repo, `tgi ask` dropped (D-TGI-4); FTS covers Russian, Spanish and English; laptop is Linux x86_64 with Docker, Antony creates the `api_id`/`api_hash` (C1–C3); keep it lean, simplest design that works; default backfill lookback 3 years per chat, configurable; single user; ~100 chats × 10–20k messages; laptop without GPU, API LLMs and embeddings allowed, local models only when CPU makes them viable; batch about every 3 h, no daemon; any stack except Rust; no Security Reviewer, but TDLib sessions and API credentials are stored sensibly and never in the repo; GitHub Actions disabled, workflow files kept valid, local runs are the CI evidence.

## 3. Stack

- **Python 3.12**, `uv` for environment and lockfile (`uv.lock` committed). Reason: TDLib, pgvector and MCP all have first-class Python support; Tinker's recommendation; nothing here needs a compiled language.
- **TDLib** through its JSON interface (the current `td_create_client_id` / `td_send` / `td_receive` / `td_execute` functions; `td_json_client_*` is deprecated) via a thin own adapter in `tgi.td` (`ctypes` over `libtdjson`). The binary is provisioned by `scripts/tdlib.sh`, which builds or installs **on the host** (a prebuilt wheel such as PyPI `tdjson` if it loads, otherwise a documented CMake build on the laptop); a `libtdjson.so` built inside a container is not used on the host because OpenSSL/libstdc++ ABI mismatches fail at load time. Rejected: third-party wrappers (`aiotdlib`, `python-telegram`) as the primary dependency; they pin a TDLib version and go stale, while the JSON interface is stable and the adapter is small. Coder may use one as a reference. **Assumption A1:** laptop is Linux x86_64 (see clarification C1).
- **Postgres 16** with `pgvector` and `pg_trgm`, run by `docker compose` (`pgvector/pgvector:pg16` image), data in a named volume, the port published **only on loopback** (`ports: "127.0.0.1:5432:5432"`; Docker's iptables rules bypass the host firewall, so a bare `5432:5432` would expose the archive to the LAN), `POSTGRES_PASSWORD` a non-default value from `.env`, database locale/collation UTF-8 (`en_US.utf8`, never `C`, so Cyrillic counts as alphanumeric for `pg_trgm` and FTS). Reason: one store gives stemming for Russian, Spanish and English (`russian`, `spanish`, `english` FTS configs), trigram matching for abbreviations and typos, and vectors; at 300k windows and 2M rows a separate search engine buys nothing.
- **psycopg 3** with plain SQL and numbered migrations (`migrations/0001_*.sql`, applied by a 40-line runner with a `schema_migrations` table). Rejected: SQLAlchemy/Alembic; the schema is six tables and the queries are search queries that want to be written by hand.
- **Embeddings:** `Embedder` port with two methods, `embed_documents(texts)` and `embed_queries(texts)` (Voyage and bge-m3 embed the two sides differently; OpenAI ignores the distinction). Providers: `voyage` (**default, D-TGI-2, model `voyage-4` since v1.9, owner decision Antony 2026-10-08**: `output_dimension=1024`, `input_type` `document`/`query`; per Voyage's docs `voyage-4` is the current general-purpose multilingual model, 1024 dims by default (256, 512 and 2048 also supported; the schema stays at 1024), 32k-token context, USD 0.06 per 1M tokens with 200M free tokens on the account, so the full backfill of 60–90M tokens is expected to fall inside the free allowance and otherwise costs about USD 4–6; all `voyage-4` series embeddings (`voyage-4-large`, `voyage-4`, `voyage-4-lite`) are mutually compatible, so `voyage-4-large` at USD 0.12 per 1M tokens is a later quality upgrade for queries or re-embeds without a schema change, though `model_mismatch` still treats a different model string as a reindex; `voyage-3.5` is Voyage's previous generation and was the default in v1.0–v1.8), `openai` (`text-embedding-3-small`, `dimensions=1024`) and `fake`. A local embedder (bge-m3 through `sentence-transformers` on CPU) is not built; it can be added later as one more class behind the same port (PLAN P2 v0.4, Design Review). Each provider declares `model` and `dim`; if `window_embedding` already holds rows with another `model`, the embed step embeds nothing, logs `model_mismatch` and the run ends with status `error` (ingestion and windows are still committed); `tgi embed --reindex` deletes the old rows and re-embeds everything after a provider change. **Assumption A2:** the model id `voyage-4` is current on Voyage's model list when Coder builds (checked 2026-10-08); if Voyage has renamed it, the newest general-purpose 1024-dim model takes its place behind the same config key (`EMBED_MODEL`), no design change.
- **MCP:** official `mcp` Python SDK (FastMCP), streamable HTTP transport for Nano, stdio for debugging; a static bearer token checked in an ASGI middleware (10 lines), see §5.6.
- **CLI:** `typer`. **Tests:** `pytest`, real Postgres from compose. **Lint/type:** `ruff`, `mypy --strict` on `tgi/`.
- Rejected: SQLite + FTS5 (no Russian stemming, no vectors without extensions); Meilisearch/Typesense/Elasticsearch (another service, no gain at this size); Telethon/Pyrogram (owner decided TDLib; also a daemon-shaped API); LangChain/LlamaIndex (no LLM in the repo, D-TGI-4); a live update daemon (owner decided batch); per-message embeddings (short chat lines embed poorly and cost ~5× more than windows).

## 4. Data model (Postgres)

```
chat           (chat_id PK bigint, account_phone text, title, kind supergroup|channel|basic_group|private,
                username null, enabled bool, added_at, backfill_done bool, backfill_years int null,
                backfill_cutoff timestamptz null,   -- added by migration 0003
                oldest_message_id bigint null, newest_message_id bigint null, last_sync_at,
                windows_dirty_from bigint null)   -- added by migration 0002
chat_tag       (chat_id FK, tag text, status proposed|confirmed, proposed_by text, PK(chat_id, tag))
message        (chat_id FK, message_id bigint, PK(chat_id, message_id), server_message_id bigint not null,
                sender_id bigint null, sender_name text, date timestamptz, edit_date timestamptz null,
                reply_to_message_id bigint null, text text not null, has_media bool,
                deleted_at timestamptz null,
                tsv tsvector GENERATED ALWAYS AS (to_tsvector('russian', text) || to_tsvector('spanish', text) || to_tsvector('english', text)) STORED)
window         (window_id bigserial PK, chat_id FK, first_message_id bigint not null, UNIQUE(chat_id, first_message_id),
                start_date, end_date, message_ids bigint[] not null, text text not null, text_hash bytea, stale bool default true)
window_embedding (window_id FK PK, model text, dim int, embedding vector(1024), embedded_at)
sync_run       (run_id bigserial PK, started_at, finished_at null, status, stats jsonb, error text null)
schema_migrations (version int PK, applied_at)
```

Indexes: `message` GIN on `tsv`; GIN `gin_trgm_ops` on `text`; btree `(chat_id, date)`; btree `(chat_id, reply_to_message_id)` (for `get_thread`); `window` btree `(chat_id, start_date)`; `window` btree `(end_date DESC, window_id DESC)` (`recent`, migration 0004, a plain `CREATE INDEX` inside the runner's transaction: it blocks window writes while it builds, so run `tgi db migrate` while no sync runs); GIN on `message_ids` (message → window mapping); `window_embedding` HNSW `vector_cosine_ops` (`m=16, ef_construction=128`), `ef_search` set per query to 200.

Rules:
- Message identity is `(chat_id, message_id)`, where `message_id` is the TDLib id (for server messages `server_id << 20`) and `server_message_id = message_id >> 20` is stored at ingest for links. Message ids are per chat, not global. Supergroup and channel `chat_id`s (`-100…`) are unique across accounts; a private or basic-group `chat_id` is per account and can collide between two burner accounts. v1 accepts this: each chat is fetched by exactly one account (`chat.account_phone`), and `tgi chats enable` refuses a private/basic-group `chat_id` already enabled under another account (documented limit; the archive is mostly supergroups). Any chat that is enabled under another account is refused as well, by `tgi chats enable` and `add_chat` alike, and its `account_phone` is never overwritten (Antony, 2026-10-09). Enables of one chat id are serialized under a transaction advisory lock, so two first enables from different accounts cannot both win (#43). A disabled supergroup or channel may move to another account.
- `text` is the message text or the media caption; empty-text messages (service messages, media without caption) are stored with `text = ''` and never indexed into windows.
- No raw TDLib object is stored (lean, #588); a later feature that needs more fields adds columns and re-syncs the sweep window.
- Accounts are not a table: an account is a directory `DATA_DIR/accounts/<phone>/` (TDLib database plus a one-line `label`); `chat.account_phone` names which one fetches the chat.
- `deleted_at` is the soft-delete tombstone (see D-TGI-3); searches exclude tombstoned messages unless asked (`include_deleted`, §5.5).
- A window is identified by `(chat_id, first_message_id)`; `window_id` is a stable surrogate for `Hit` and `window_embedding`. A rebuild upserts on that key, so an unchanged window keeps its row and embedding; `backfill_years` overrides `BACKFILL_YEARS` for one chat. `backfill_cutoff` is the cutoff in force when the backfill last finished, `null` when it never finished or finished before this column existed.
- `windows_dirty_from` is the persisted window-rebuild marker (decision #632, option b): the lowest `message_id` written, edited, tombstoned, restored or purged in this chat since windows were last rebuilt, `null` when windows are current. Every writer (catch-up, backfill, sweep, `--resweep-days`) sets `windows_dirty_from = least(coalesce(windows_dirty_from, id), id)` **before** the message write it covers, in the same transaction where one exists; under autocommit the marker statement simply comes first, so a crash between the two leaves at most a harmless extra rebuild. The window step clears it to `null` in the same transaction that upserts the rebuilt windows. Reason over an in-memory map (option a): the map dies with the process, and a crash between the sweep and the rebuild would leave stale windows and embeddings until the same range happens to be touched again, which for an edit or a deletion may be never; one nullable column and a two-line migration make the hand-off crash-safe with the same code path in the normal case, and nothing in stored data can otherwise tell an edited message from an unchanged one.
- Vector dimension is fixed per migration at 1024 (both default providers can emit 1024). A provider with another dimension is a migration that recreates `window_embedding`; `model` on each row makes partial re-embeds detectable.

## 5. Behaviour

### 5.1 Accounts and secrets
`tgi accounts add --phone +34...` runs the TDLib authorization state machine interactively: phone → code → 2FA password (never stored, read from the terminal). TDLib's own database lives at `DATA_DIR/accounts/<phone>/td/` with `use_message_database=false` (TDLib is the transport, Postgres is the store), encrypted with `TDLIB_DB_KEY`. Secrets come from `.env` (gitignored, mode `0600`; `.env.example` committed with placeholders): `TG_API_ID`/`TG_API_HASH`, `TDLIB_DB_KEY`, `DATABASE_URL` (with the non-default `POSTGRES_PASSWORD`), `VOYAGE_API_KEY` (optional `OPENAI_API_KEY` for the `openai` provider), `MCP_TOKEN`. There is no LLM key (D-TGI-4). `VOYAGE_API_KEY` is either the real key or a placeholder when the laptop routes `api.voyageai.com` through the OneCLI proxy, which injects the real one; the provider does not care which. `DATA_DIR` is outside the repo; `tgi` creates `DATA_DIR/accounts` with mode `0700` and warns at startup when `.env` is more open than `0600`: the TDLib session grants full account access, so `TDLIB_DB_KEY` next to it adds little, and the directory is kept out of backups and sync tools (documented in README). Logging never prints message text, phone codes, passwords, keys; message ids and chat ids are fine.

### 5.2 Chats and tags
`tgi chats list --account <phone>` shows the account's dialogs; `tgi chats enable <chat_id>` adds to the allowlist (one account per chat); `tgi chats disable <chat_id>` stops syncing and keeps data; `tgi chats forget <chat_id>` deletes the chat's messages, windows and embeddings (asks for confirmation). `tgi chats add <link> --account <phone> [--years N]` joins a supergroup or channel from a link and enables it, the same join as the MCP `add_chat` tool (§5.6; shared code, same refusals, under the sync lock), so chats can be added without MCP, and with `MCP_READ_ONLY`. `tgi tags propose|confirm|remove` manage `chat_tag`; the MCP `suggest_tags` tool can only write `proposed` rows. Search filters by tag use **confirmed** tags only.

### 5.3 Sync (`tgi sync`, every 3 h by cron or a systemd timer; one process at a time via a Postgres advisory lock; `--max-minutes 150` budget so runs never overlap)
Chats are processed in `last_sync_at` ascending order (nulls first); `last_sync_at` is set when the chat's turn in a run ends, whether it completed or was cut off by the budget or a flood limit, so a chat that keeps exhausting the budget moves to the back of the next run and cannot starve the others. Per enabled chat, in this order, each step checkpointed in `chat` so a crash resumes:
1. **Catch-up:** `getChatHistory(from_message_id=0, limit=100)` paging backwards until a page's oldest `message_id` is `≤ newest_message_id` (so a deleted checkpoint message cannot cause a full re-page) or the page is empty; upsert all; `newest_message_id` is advanced **only after catch-up completes** (the old checkpoint was reached or an empty page came back), never per page: a run interrupted mid catch-up (flood limit, `--max-minutes`, crash) keeps the old checkpoint and the next run re-pages from the top, so no gap can form. **Jump over the stored range:** because every interrupted run pages down from the top, the stored messages above the checkpoint always form one contiguous range; when a fetched page contains only messages that are already stored (or skipped, see below), catch-up sets `from_message_id` to the lowest stored `message_id` above `newest_message_id` (one `min()` query) and continues below it, so each run adds at least `budget − 2` new pages and a gap of `n` pages closes within about `n / (budget − 2) + 1` runs. The stop rule is checked before the jump. A message whose `message_id` is not divisible by `2^20` (not a server message) is skipped and logged with its ids only; it is not fatal to the chat's catch-up and counts as stored for the jump. **First run** (`newest_message_id` null): take the first page only, set `newest_message_id` and `oldest_message_id` from it, and hand the rest to backfill.
2. **Backfill** (if `backfill_done=false`): page backwards from `oldest_message_id` until TDLib returns an empty page **or the page's oldest message is older than the chat's lookback cutoff**, where the lookback is `coalesce(chat.backfill_years, BACKFILL_YEARS)` years (`BACKFILL_YEARS` 3, configurable; `tgi chats enable --years N` stores the per-chat value) and the cutoff is now minus that many years; messages older than the cutoff are not stored; set `backfill_done=true` and `backfill_cutoff = cutoff`. Backfill is interleaved across chats (one page per chat per round) so a 20k-message chat does not starve the others. **Budget reserve (v1.12):** the backfill stops at `(1 − BACKFILL_RESERVE)` of the run's budget (`BACKFILL_RESERVE` 0.2); the sweep, the window step and the embed step get the rest, so a long history fetched over several runs does not keep them from running (they share at most that reserve; a catch-up that runs long leaves them less). A flood wait the backfill could not wait out stays in force for the account: the sweep waits for it within the budget or the run ends `time_limited`. A run whose backfill stopped there ends `time_limited`; a flood limit still ends the run at once. **Deepening:** at the start of a run, a chat with `backfill_done=true` whose cutoff is now earlier than its `backfill_cutoff` (a larger `--years`, a larger `BACKFILL_YEARS` for a chat without its own value), or whose `backfill_cutoff` is `null`, is reopened: `backfill_done=false` and `oldest_message_id` = the oldest stored `message_id`, so backfill continues downward from the stored range without refetching it, or `0` (the top) when the chat holds no stored message, the one case that re-pages a chat; new messages flow through the normal window rebuild and only new or changed windows are embedded (changed includes a window whose reply quote can now be rendered because its parent was just stored). A smaller lookback is stored and deletes nothing; raising it again refetches nothing. `tgi chats enable` reports whether the next sync will continue the backfill.
3. **Edit/delete sweep:** re-page the last `SWEEP_DAYS` (7) days; a stored message whose `edit_date` changed is updated; a stored, non-tombstoned message absent from the re-fetched range is handled per `ON_DELETE` (default `tombstone`, D-TGI-3): `tombstone` sets `deleted_at = now()` and hides it from search, `purge` deletes the row (detection is the same either way); a tombstoned message that reappears is un-tombstoned. **Absence counts only when the sweep is complete:** the chat's sweep must have received a message older than the cutoff or reached the chat start; a sweep cut short by a flood wait, `--max-minutes` or an error tombstones nothing for that chat, and a message is considered absent only if its `date` lies inside the fully paged range. **An empty page is trusted as the chat start only when the archive agrees:** if the chat still holds a stored, non-tombstoned message dated inside the sweep window that the empty page should have covered (any such message for the first page; for a later page, one with `message_id` below the page cursor), the sweep is treated as cut short: it deletes nothing, is logged with the chat id only, and the next run simply sweeps again. Without this, one spurious empty response (for example on a cold session) would tombstone, or under `ON_DELETE=purge` irreversibly delete, every stored message in the window. The guard does not block real deletions: a chat whose window messages were all deleted but whose older messages remain returns those older messages on its first page, so the sweep completes and the window rows are handled per `ON_DELETE`; a chat whose whole history lies inside the window and lost some messages is handled once its remaining messages age past the cutoff (at most `SWEEP_DAYS` later). Only a chat emptied entirely while enabled is never swept clean: its rows stay, the log line repeats each run, and `tgi chats forget` is the remedy (documented limit, accepted instead of a confirmation call the port does not offer). `tgi sync --resweep-days N <chat_id>` runs the same sweep over a deeper range by hand (§7). Rationale: TDLib only delivers `updateDeleteMessages`/`updateMessageEdited` while connected, so a batch client must look.
4. **Flood wait:** on TDLib error 429 (`Too Many Requests: retry after N`) the chat's step sleeps `N` seconds then retries; after three consecutive flood waits the run ends early with status `flood_limited` and the remaining chats wait for the next run. Page requests are spaced `PAGE_DELAY_MS` (300) apart per account.
5. **Windows:** for every chat with `windows_dirty_from` not null (the in-memory touched map of earlier drafts is gone), rebuild windows from the window that precedes that message id onward (the window with the greatest `first_message_id < windows_dirty_from`, else the chat start; a purged id still marks its position). Strictly `<`, not `≤`: when the marker is itself a window's first message, the previous window may absorb the messages that follow it in a from-scratch build, so starting at the marker's own window would leave a split that a from-scratch rebuild would not produce (§5.4), upserting on `(chat_id, first_message_id)`; a window whose `text_hash` changed is marked `stale`, an unchanged one keeps its embedding, windows no longer produced are deleted (their embeddings cascade); the marker is cleared in the same transaction, so a crash during the rebuild repeats it next run.
6. **Embed:** stale windows are embedded in batches of 64 through the configured provider, newest first (`end_date` desc, then `window_id` desc; v1.12, so a backlog delays old history rather than the latest conversations); an embedding failure leaves the window `stale` for the next run and does not fail the run. The run record (`sync_run`) stores counts: fetched, upserted, edited, tombstoned, windows rebuilt, embedded, flood waits.
7. **Run status, stale runs and exit codes (owner-approved, #630):** `sync_run.status` takes exactly `running`, `ok`, `time_limited`, `flood_limited`, `interrupted`, `error`; the column is plain `text` with no CHECK constraint, so `interrupted` needs no migration. A run that dies without reaching its `finally` (SIGKILL, power loss, OOM) leaves its row at `running`; the next run, right after it has taken the advisory lock and before inserting its own row, sets every leftover `running` row to `status = 'interrupted', finished_at = now()` (the lock guarantees no such row belongs to a live run). `tgi sync` exits **0** for `ok`, `time_limited` and `flood_limited`, which are normal partial runs that cron or the timer must not log as failures (the status and stats are on stdout); **2** when another run holds the lock (`SyncLocked`, message on stderr, no `sync_run` row); **3** when the run ends with status `error` (the sanitized error type on stderr, never TDLib payloads or message text); **1** stays Typer's usage/config error (bad option, missing `.env` key). No other exit codes exist. **TDLib and the lock (v1.12):** `tgi sync` closes its TDLib clients when the TDLib steps end, before the window and embed steps and before it releases the lock; `tgi chats list`, `tgi chats enable` and `tgi chats add` take the lock around their TDLib use and exit 2 while it is held (`tgi accounts add` and `tgi td spike` are run by hand, need no database, and do not). The repository ships `deploy/tgi-sync.service` and `deploy/tgi-sync.timer` (every 3 h, `Persistent`, exit 2 counted as success).

### 5.4 Conversation windows
Within one chat, messages ordered by `(date, message_id)`, skipping empty text. A new window starts when the gap to the previous message exceeds `WINDOW_GAP_MIN` (30 minutes), or the window would exceed `WINDOW_MAX_CHARS` (1 500) or `WINDOW_MAX_MSGS` (40). `WINDOW_MAX_CHARS` counts only the `<sender>: <text>` lines, not the header line, the newlines or the `↪` reply prefixes, so the stored window text can run a little over the cap: the cap bounds size loosely and the embedding input limit is far larger (accepted, Tinker #648). A message replying to a message outside its window prefixes the quoted parent's first 200 characters as `↪ <sender>: …` (context only; the parent stays a member of its own window). Window text = `[<chat title>] <date>\n<sender>: <text>\n…`. A single message longer than `WINDOW_MAX_CHARS` becomes a window of its own with the text truncated to `WINDOW_MAX_CHARS` (the stored message is untouched). Windows are deterministic from the messages, so rebuilding a chat from a window boundary reproduces the same windows and `text_hash` prevents needless re-embedding; because the chat title is part of the text, renaming a chat re-embeds that chat (accepted, rare). Tombstoned messages leave their windows (which are rebuilt).

### 5.5 Search core
`search(queries: list[str], *, tags=None, chat_ids=None, since=None, until=None, mode="hybrid"|"keyword"|"semantic", limit=20, include_deleted=False) -> list[Hit]`.
1. Resolve filters first: tags → chat ids (confirmed tags only); date range on `message.date` (keyword) and on `window.start_date/end_date` (semantic).
2. **Keyword leg:** for each query, `websearch_to_tsquery('russian', q) || websearch_to_tsquery('spanish', q) || websearch_to_tsquery('english', q)` (OR of the three) against `tsv`, plus a trigram leg for short tokens (≤ 6 characters, e.g. `ВНЖ`, `TIE`) using strict word similarity, `q <<% text` with `SET LOCAL pg_trgm.strict_word_similarity_threshold = 0.5` (indexable by `gin_trgm_ops`; plain `similarity()` against a whole message never reaches a threshold, and non-strict `word_similarity('tie','tiene')` = 0.75 would flood Spanish results), ranked by `ts_rank_cd` (trigram-only hits by `strict_word_similarity`); top `K=100` messages, mapped to their windows.
3. **Semantic leg:** embed each query with the same provider; top `K=100` windows by cosine distance under the filters.
4. **Fusion:** reciprocal rank fusion (`k=60`) over windows across all legs and all queries; return `limit` windows.
5. `Hit = { window_id, chat_id, chat_title, tags, start_date, end_date, score, messages: [{message_id, sender_name, date, text, link}], highlights: [str] }`. `link` is `https://t.me/c/<chat_id without -100>/<server_message_id>` for supergroups and channels, `https://t.me/<username>/<server_message_id>` when the chat has a username (never the TDLib `message_id`, which is `server_id << 20`), and `null` for basic groups and private chats (no deep link exists; the answer cites chat title and date instead).

With `include_deleted=True`, keyword hits on tombstoned messages (which belong to no window) are returned as single-message hits: `window_id = null`, `start_date = end_date = message.date`, one message. Query expansion and translation (ВНЖ / residencia / TIE / renovación) are the agent's job: it passes several `queries`; the core never rewrites them.

**Date-time bounds:** `since`/`until` take a date (a whole UTC day, as before) or a date-time, an exact inclusive instant (UTC when it has no zone), so a rolling period ("the last 12 hours") can be expressed.

**`recent(*, since=None, until=None, tags=None, chat_ids=None, limit=20, cursor=None, now=None) -> Recent`** answers "what's new" without a query. The range is `since ≤ date < until`: unlike `search`, `until` is exclusive (a date: up to the end of that UTC day) and defaults to `now`, so consecutive ranges meet without gap or overlap and nothing posted after `now` is listed (the bound is posting time: a page fetched later can include a message stored meanwhile but posted before `now`). It returns windows (confirmed-tag and chat filters as above) whose span overlaps the range (`end_date ≥ since`, `start_date < until`), ordered by `end_date` desc, `window_id` desc (index `window_end_idx`, migration 0004); each `Hit` keeps only its messages dated inside the range (`get_context` widens it), with `score` 0 and no highlights, and a window with none inside is skipped. Paging is keyset: when the page was full, `next_cursor` encodes the frozen range, the filters and the last window's `(end_date, window_id)`; with `cursor`, range and filters come from it and the other arguments are ignored. A page may be short or empty and still have more; only a null `next_cursor` ends it. Paging runs over live data: a sync between pages that moves a window's `end_date` can make it repeat or drop out (accepted; digests should run after a sync). `Recent = {now, since, until, hits, next_cursor}`. Messages not yet in a window (stored by a sync whose window step has not run) and tombstoned ones are not listed. The CLI is `tgi recent`.

### 5.6 MCP server (`tgi mcp --http | --stdio`)
**Transport (D-TGI-1):** streamable HTTP, served by `tgi mcp --http` on the host, bound to `MCP_BIND`, default `127.0.0.1:8765`. The address the Nano container reaches is an explicit setting chosen at registration time: typically the gateway address of the Docker network the container is on (`172.17.0.1` for the default bridge, reachable as `host.docker.internal` with `--add-host=host.docker.internal:host-gateway`; a user-defined network has its own gateway, so a fixed `172.17.0.1` is not assumed anywhere). The startup guard accepts a loopback address or an address assigned to a local interface named `docker*` or `br-*` (read from `ip -j addr`), and refuses `0.0.0.0`, `::` or any other address unless `--allow-any-bind` is given. Run by a systemd user service. `--stdio` keeps the same tools for local debugging. **Auth:** one static bearer token, `MCP_TOKEN` in `.env` (≥ 32 random bytes, generated by `tgi mcp token`), required on every request and compared with `hmac.compare_digest`; a missing or wrong token is `401` with no body detail, and the server logs the count, never the token. On the Nano side the token is injected by the credential gateway, not stored in agent configuration (NanoClaw convention); the registration itself is out of scope here. Justification: a Docker network is shared by every container on it and the archive is Antony's private chat history; one header check is the cheapest guard that makes a stray container harmless. Rejected: mTLS and OAuth (nothing here needs identities), no auth at all (any container on the bridge could read the archive).
Tools, all read-only except `suggest_tags` and `add_chat`. Every tool carries MCP annotations: the six read tools `readOnlyHint: true, openWorldHint: false`; `suggest_tags` `readOnlyHint: false, destructiveHint: false, idempotentHint: true, openWorldHint: false`; `add_chat` the same but `openWorldHint: true`. They let a client run reads unattended and ask the user before a write (Hermes asks for any tool without `readOnlyHint` on a server it marks `untrusted`); they are hints. **`MCP_READ_ONLY`** (`1`/`true`/`yes`/`on`; default off, so the tool set is unchanged) is enforced by the server: `suggest_tags` and `add_chat` are not registered (a call is `unknown_tool`) and `tgi mcp` never opens the Telegram account.
- `list_chats(tag?: str) -> [{chat_id, title, kind, tags, message_count, first_date, last_date}]`
- `list_tags() -> [{tag, status, chat_count}]`
- `search(queries: [str], tags?: [str], chat_ids?: [int], since?: date|datetime, until?: date|datetime, mode?: str, limit?: int) -> [Hit]`
- `recent(tags?: [str], chat_ids?: [int], hours?: int, since?: date|datetime, until?: date|datetime, limit?: int, cursor?: str) -> {now, since, until, hits: [Hit], next_cursor}` (§5.5 `recent`): `hours` (1–744, default 24) counts back from the server clock and excludes `since`; `until` needs `since`; a `cursor` alone continues a listing (its range and filters win, other arguments but `limit` are ignored); the answer carries the server's `now` so an agent without a clock can state the period. Date arguments of `search` and `recent` are parsed as a date when they are `YYYY-MM-DD` and as a date-time otherwise (a midnight date-time stays an instant). Errors: `bad_argument` (both `hours` and `since`, `until` alone, a cursor the server did not return, an unparsable date), `bad_range`, `unknown_tag`, `unknown_chat`.
- `get_thread(chat_id, message_id, limit=50) -> [Message]` (the reply chain up to the root and replies to it)
- `get_context(chat_id, message_id, before=10, after=10) -> [Message]`
- `suggest_tags(suggestions: [{chat_id, tag, reason}]) -> {proposed: n}` (writes `proposed` rows only)
- `add_chat(link: str, years?: int) -> {chat_id, title, kind, username, backfill_years, sync}` (Antony, 2026-10-09): joins the chat behind `link` (`https://t.me/name`, `@name`, an invite link `https://t.me/+hash` / `t.me/joinchat/hash`, a chat id or a `t.me/c/<id>/<n>` message link) with the account `MCP_ACCOUNT` (default: the only logged-in one) and adds it to the allowlist like `tgi chats enable`; the next `tgi sync` fetches it. Only supergroups and channels, public or invite-only (private-link) alike: the agent may join invite-only groups (Antony, 2026-10-09). A private chat or a basic group is refused before anything is joined (`not_allowed`), so the agent cannot open Antony's direct messages to itself. A chat already enabled under another account is refused too (`not_allowed`), and the second account does not join it. The one exception is an invite link to a chat that this account cannot see before joining, because TDLib gives no chat id before the join: there the join happens, and the refusal comes at enable, with nothing in the database changed. There is no cap on how many chats the agent may join, by decision (Antony, 2026-10-09). An invite link that sends a join request is `join_pending` (nothing is enabled). It takes the sync lock, because a running `tgi sync` holds the account's TDLib session: during a sync it answers `busy`. Other codes: `not_found` (no such username or a dead invite), `flood_wait`, `telegram_error`, `not_configured` (no account, or several without `MCP_ACCOUNT`). The result's `sync` block estimates when the chat is searchable (`tgi.eta`): `next_run_at` from `SYNC_EVERY_MINUTES` (the host's timer, 0 to 10080; unset → no times), `estimated_messages` from the daily rate of the newest one or two history pages times the lookback (capped by the newest server message id), `estimated_minutes` from the throughput of the last runs divided among the chats still backfilling (backfill is interleaved), `searchable_from` (the newest messages, a few minutes into the next run) and `complete_by` (whole lookback, counting each run's `--max-minutes` budget and the wait for the next tick). If the history sample fails (a TDLib error or flood wait, even on its second page), `estimated_messages`, `estimated_minutes` and `complete_by` are null: an unread chat is not an empty one. The estimate is best effort: it runs after the chat is enabled, and if it fails the call still succeeds, with every `sync` field null. Rough by design; the agent passes the times on to the user.
Errors follow MCP tool-error convention with a `code` (`unknown_chat`, `unknown_tag`, `bad_range`, `embedder_unavailable`). Result sizes are bounded (`limit ≤ 50`, context ≤ 100 messages).

### 5.7 Reference query without an LLM in the repo (D-TGI-4)
There is no `tgi ask` and no LLM dependency in this repo: Nano is the agent. The reference query is exercised by a scripted MCP client (`tests/e2e/reference_query.py`, also runnable as `tgi selftest`) that does what the agent would: `list_tags` → `search(queries=["продление ВНЖ", "ВНЖ renovación", "renovación TIE", "residence permit renewal"], tags=["valencia"], since=<30 days>)` → `get_context` on the top hit, and checks the links. Hybrid search has no relevance cutoff: the semantic leg always returns its nearest `K` windows under the filters, so unrelated windows inside the filters appear at the tail of the list rather than being dropped; relevance is expressed by rank, and the agent reads the top hits, not the whole list. The prompt guidance for the agent (expand and translate across RU/UK/ES, filter by tags and dates, cite links) ships as `docs/AGENT-NOTES.md` for whoever registers the server in Nano.

## 7. Risks

- **TDLib provisioning** is the one thing that can stall the first day: no official prebuilt `libtdjson`, and a source build is 30–60 min and memory-hungry. Mitigation: a spike task first in the plan (Coder delivers `scripts/tdlib.sh` and the adapter; Antony runs the login and one `getChatHistory` page on the laptop, since the phone code and 2FA are his), the script documents both paths and builds on the host (ABI, §3), and the adapter is isolated so a wrapper library can be swapped in if the build is the problem.
- **Deletion detection is heuristic.** The 7-day sweep catches deletions inside the window; older deletions are never noticed. Stated as a known limit; a `tgi sync --resweep-days 365 <chat_id>` escape hatch exists for a manual deep sweep.
- **`getChatHistory` paging** returns fewer messages than `limit`, sometimes one, and the first call after a cold start can return only cached messages; the paging loop must advance on `from_message_id = last returned id` and treat "fewer than limit" as "keep paging", stopping only on an empty page. The fake client reproduces both behaviours.
- **Burner accounts and rate limits.** Paging 2M messages across 100 chats at 300 ms per page is ~20k pages ≈ 2 hours of requests spread over several runs; Telegram's limits for history reads are generous, but a fresh account that only reads history is a pattern Telegram sometimes restricts. Mitigation: per-account spacing, flood-wait obedience, early end of a run. Residual risk accepted by the owner's choice of burner accounts.
- **Filtered vector search recall.** HNSW with a `WHERE chat_id = ANY(...)` filter can return fewer than K rows when the filter is selective; `ef_search=200` and an exact fallback (`SET LOCAL hnsw.ef_search`; if fewer than `limit` rows, rerun the semantic leg with a sequential scan over the filtered set) keep recall honest at this size.
- **Voyage rate limits on a new account** (tier limits apply until some paid usage accrues): the embed step honours `429` with the `Retry-After` header and keeps the remaining windows `stale` for the next run, so the first backfill may take several runs to embed fully; search works meanwhile on the keyword leg plus whatever is embedded. Request size stays under Voyage's per-call limits (batches of 64 windows, ≤ 1 500 chars each).
- **Window instability under edits** re-embeds a handful of windows per edit; bounded by `text_hash` and acceptable at 3-h cadence.
- **One MCP token for reads and writes:** a single `MCP_TOKEN` covers the read tools as well as `suggest_tags` and `add_chat`. There is no separate write token, by decision (Antony, 2026-10-09); this is a known limitation. An owner who does not want any token holder to join chats sets `MCP_READ_ONLY` and adds chats with `tgi chats add`.
- **Secrets:** `.env` and `DATA_DIR` are outside git (`.gitignore` committed with them); TDLib's database is encrypted with `TDLIB_DB_KEY`; no test fixture contains real data.
- **Network exposure (D-TGI-1):** the listeners are Postgres on `127.0.0.1:5432` (compose, non-default password) and the MCP server on `MCP_BIND` (loopback by default, a Docker-network gateway address when registered) with a bearer token; it has two write tools (`suggest_tags`, proposed rows only; `add_chat`, which joins and enables supergroups and channels only, so a token holder can widen the archive to any public or invite-only supergroup or channel the account can join, but never to private chats) and never returns secrets. The bind check at startup and A12 keep it off the LAN; the token lives in `.env` on the host and in the gateway on the Nano side. Plain HTTP on a Docker network is accepted: traffic never leaves the host.

## 8. Acceptance criteria

All checks run locally with `make ci` (= `uv run ruff check`, `uv run mypy`, `uv run pytest`) against the compose Postgres, and `.github/workflows/ci.yml` runs the same three commands with a `pgvector/pgvector:pg16` service, kept valid (`actionlint` in `make ci`) while Actions stay disabled. A green local run plus its pasted output is the CI evidence.

Verifiable without Telegram (fixtures: `FakeTdClient` driven by JSON scenarios under `tests/scenarios/`; `FakeEmbedder` = deterministic token-hash vectors). The fakes are the only test doubles; everything else runs for real against Postgres:
- **A1 Migrations:** `tgi db migrate` on an empty database creates the §4 schema with the two extensions (`vector`, `pg_trgm`) and every §4 index; re-running is a no-op.
- **A2 Backfill:** scenario with 3 chats × 2 500 messages, pages of uneven size (100, 37, 1, …), one chat with messages older than the lookback → all messages inside the lookback stored exactly once, none older, `backfill_done`, checkpoints set; killing the run mid-way (scenario raises after page N) and re-running completes without duplicates. A chat whose backfill finished at 1 year and is re-enabled with `--years 3` continues from its oldest stored message on the next sync, stores exactly the messages between the two cutoffs once, re-embeds only the new windows, the windows re-segmented up to the first gap after the old boundary and a window after that gap holding a reply to a newly stored parent (its quote now renders), while a window after the gap without such a reply keeps its embedding, and reports `backfill continues to 3 years on the next sync`; `--years 1` after that deletes nothing and the next sync fetches nothing; a chat whose first page was entirely older than a 1-year lookback (nothing stored, backfill finished) re-pages from the top after `--years 3` and stores every message inside the new lookback.
- **A3 Catch-up and sweep:** scenario adds 50 new messages, edits 5 (new `edit_date`, new text), deletes 7 inside the sweep window and 3 outside → the 50 are stored, the 5 updated, the 7 tombstoned (`ON_DELETE=tombstone`) or gone (`purge`), the 3 untouched (documented limit), windows of the affected ranges rebuilt and only those marked `stale`; a run killed (scenario raises) after the sweep and before the window step leaves `windows_dirty_from` set, and the next run rebuilds exactly those windows and clears it; a run whose sweep is cut short by a flood wait after the first page tombstones nothing; a sweep whose first page comes back empty (fake fault `empty`) while the window still holds live stored messages tombstones or purges nothing and logs the chat, and the next run (no fault) sweeps normally; a chat whose window messages were all deleted while older messages remain has them tombstoned or purged on that same sweep; a catch-up whose `newest_message_id` message was deleted stops after one page past it and stores only the new messages; a catch-up interrupted after page 1 of 3 (scenario raises) leaves `newest_message_id` unchanged, and the re-run stores all new messages with no gap.
- **A4 Flood wait:** scenario injects two 429s with `retry after 2` → the run sleeps (clock faked) and completes; three consecutive → run status `flood_limited`, remaining chats untouched, and the `tgi sync` process exits 0 (likewise for `time_limited`); a row left at `running` by a previous run is `interrupted` with a `finished_at` after the next run starts; a second `tgi sync` while the lock is held exits 2 without a `sync_run` row; a run ending in `error` exits 3. **Stuck-chat case:** chat A has 1 000 new messages and every run is cut to 4 page requests by a scenario `flood_limited`; chat B has 50 new messages → A's catch-up completes within 6 runs with every message stored exactly once and no gap, B is caught up by the end of run 2, and `last_sync_at` ordering puts A behind B after its first cut-off turn.
- **A5 Windows:** a fixed scenario yields the expected windows (gap, size and reply-prefix rules each exercised); rebuilding twice gives identical `text_hash`.
- **A6 Keyword search:** Russian stems match (`продление` finds `продлении`), Spanish stems match (`renovación` finds `renovaciones`), English stems match (`renewal` finds `renewals`), `ВНЖ` finds `внж` and a 40-word message containing `ВНЖ,` via the trigram leg, and `TIE` does **not** match a message containing only `tiene`; tag and date filters restrict; tombstoned messages excluded unless `include_deleted`.
- **A7 Hybrid search:** with `FakeEmbedder`, a window sharing tokens with the query ranks in the top 5 of the semantic leg; RRF merges both legs; `limit` and bounds hold; the selective-filter fallback returns `limit` rows when enough exist.
- **A8 MCP:** the server starts over streamable HTTP on a loopback test bind and over stdio; with the token `list_chats`, `search`, `get_thread`, `get_context`, `suggest_tags` answer with the §5.6 shapes; without or with a wrong token every request is `401` and the log has no token; `suggest_tags` writes only `proposed` rows; tag filters ignore `proposed` tags; every tool lists its annotations; with `MCP_READ_ONLY` only the six read tools are listed, the write tools answer `unknown_tool` and Telegram is never opened.
- **A9 Reference query (plumbing):** scenario with chats tagged `valencia`, messages about ВНЖ renewal in RU, `renovación TIE` in ES and `residence permit renewal` in EN in the last 30 days, plus distractors (other tags, older dates, unrelated topics) → the scripted MCP client of §5.7 over HTTP returns hits whose messages include ≥ 3 of the seeded ones with correct links; no hit comes from a distractor outside the filters (other tag, older than 30 days); every hit from an unrelated-topic distractor inside the filters ranks below every seeded hit (hybrid search has no relevance cutoff, §5.7).

## 9. Rejected alternatives (summary)

SQLite FTS5 (no Russian stemming, no vectors); separate search engine (extra service, no gain); Telethon/Pyrogram (owner decided TDLib; daemon-shaped); live daemon (owner decided batch); per-message embeddings (poor quality, higher cost); ORM + Alembic (six tables, hand-written search SQL); a real-LLM `ask` command in the repo (Nano is the agent, D-TGI-4); mTLS/OAuth or no auth on the MCP listener (§5.6); Rust (excluded by the owner).
